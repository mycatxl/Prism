# 个人版：同出口分组、百万节点、检测与 IP 切换

日期：2026-09-05。状态：方案比较与推荐，未实现，容量数字是工作量示例而非已完成的压测结果。关联：[总设计](../DESIGN.md)、[标签与质量规则](QUALITY_AND_ROUTING.md)、[安全](SECURITY.md)。

## 1. 四种对象不要合并成一张记录

| 对象 | 保留原因 |
|---|---|
| 订阅来源 | 保存刷新地址、周期、原始标签、删除与引用关系 |
| 节点配置 | 相同配置按 hash 去重，不同协议、地址、凭证仍是独立线路 |
| 出口 IP 组 | 将当前观测为同一出口的线路逻辑分组，共享 IP 质量证据 |
| 平台会话 | 指定某个使用场景当前绑定哪个出口，可手动或定时切换 |

一个订阅通常含多个 IP，一个 IP 也可能出现在多个订阅中。因此合并的是出口视图，不是订阅实体，不删除不同线路的参数与来源。

示例：订阅 A 的 VLESS 节点、订阅 B 的 SOCKS5 节点、手动导入的 HTTP 节点，观测出口都为 `203.0.113.10`。展示为一个出口组三条线路，但每条线路各有健康、延迟、协议、优先级和有效期。示例地址仅用于说明。

分组键至少考虑规范化 IP 和 IP family；线路的成员关系还受网关、探测 profile、观测时间和配置 revision 约束。相同 IP 不证明同一物理设备或同一供应商，分组不能推导共同控制权限。

## 2. 同 IP 线路选择

先对每条线路应用平台标签、启停、协议、网络健康等规则，再形成该平台的出口组。不得将线路 A 的允许标签与线路 B 的健康状态拼接，借此绕过筛选选择 B。

推荐两层选择：

```text
平台筛选后的独立出口组
  -> 粘性租约命中，或按独立 IP 的负载/延迟选择出口组
  -> 在该组的合格线路内选择优先级和可用线路
```

这样一个 IP 拥有几十条重复线路时，不会仅因节点数量多而在随机池里被反复偏爱。质量证据可共享，但同 IP 的每条线路仍要证明自身可连接。

提供三种组内策略：

| 策略 | 选择方式 | 适用场景 |
|---|---|---|
| 优先级故障切换，建议默认 | 优先当前可用的最高等级线路，同等级再比较延迟/负载 | 明确想优先某几个节点或订阅 |
| 同等级均衡 | 只在当前最高可用等级内按权重或 P2C 分配 | 避免单线路过载 |
| 固定线路 | 只使用指定线路，故障则按显式配置拒绝或启用备选 | 调试、固定传输路径 |

优先级可由平台引用的节点列表、来源或受限标签规则配置；优先级不能覆盖质量或安全排除规则。稳定会话默认不因某条更高优先级线路刚恢复就反复搬迁，可在冷却期后对新连接重新优化。

组内首选连接失败时，连接建立阶段允许有上限地尝试其他合格线路，例如最多两条；已经发送可能产生业务效果的数据后，不能无条件重放请求。已有 TCP 隧道不能直接移植到另一条线路。

Resin 已有粘性租约失效时同 IP 轮换的基础，但当前候选选择会扫描平台视图。大规模时增加有界 `IP -> 合格线路索引`，避免为一次故障扫描百万条记录。

## 3. 百万节点首先是资源模型问题

定义三个规模：`N` 为已存储的节点配置数，`A` 为处于活跃运行/检测集合的线路数，`U` 为有有效观测的独立出口 IP 数。容量和成本分别按 N、A、U 建模，不能只写“支持百万节点”。

一百万行不超出 SQLite 作为数据库的常见使用范围。实际限制来自记录大小、索引、更新频率、读写模式、磁盘和运行态资源。

因此个人版的数据库决策是：`SQLite = 默认库存与本地状态库`，不是“所有节点都驻留内存的运行时数据库”。一百万条冷库存可以接受；一百万条都创建 Outbound、持续保持连接或按秒级频率写状态则不接受，必须先降低活跃集合或增加执行器。

若每条原始配置平均 2 KiB，一百万条仅原始配置约 1.9 GiB，尚未计索引、标签引用、历史、日志和 WAL。若每条活跃节点在内存中平均占 10 KiB，一百万条约 9.5 GiB，尚未计连接缓冲、解析器和其他组件。这些是假设计算，不代表 Resin 的实测开销。

当前 Resin 的内存全局节点池和 Outbound 初始化方式不应未经压测就按百万活跃节点上线。必须将协议实现继承与库存/运行态资源管理的扩展区分开。

### 3.1 存储方案比较

| 方案 | 优势 | 局限 | 推荐阶段 |
|---|---|---|---|
| SQLite + 本地运行态 | 部署简单，事务与索引完备 | 单库单写，长读与大批更新影响 WAL 和尾延迟 | 个人版默认，按实际百万库存测试验收 |
| PostgreSQL + 本地运行态 | 适合多个写入服务、集中历史和多机器管理 | 引入服务运维，仍不能解决百万 Outbound 占内存 | 多写入者或多机器成为真实需求时 |
| 库存分片/多检测执行器 | 可扩展探测吞吐和磁盘容量 | 跨执行器健康、去重和观测一致性更复杂 | 单机预算被实测证明不足后 |

SQLite 使用 WAL、批量事务、短读事务、每库一个受控写入队列；不同一致性等级可拆配置、质量、运行缓存和滚动日志库。不能在每次探测后都同步单条 fsync，也不能让日志写入阻塞配置操作。

查询使用索引与 keyset 游标，限制返回条数。节点原始 JSON 和大证据按需读，不把每个列表请求变为百万行反序列化。普通历史按小时/天聚合，避免每次高频健康检查都永久追加明细。

迁移 PostgreSQL 的触发条件是实测写队列年龄、WAL 体积、查询 p99、恢复耗时或多写入者需求超过预算，不以达到某个行数自动切库。

### 3.2 热、温、冷分层

- 冷库存：原始配置、来源引用、历史结果主要在数据库，按计划获得检测机会。
- 温索引：紧凑节点摘要、出口组、最近健康、标签/规则版本；不要求每个节点都有常驻 Outbound。
- 热集合：当前平台实际使用、近期需要检测的线路，建立有界 Outbound 和连接缓存。

Outbound 按需创建，同节点并发创建合并；淘汰只能关闭空闲且无引用的实例，不破坏活动连接。活跃集合大小、每 IP 备用线路数、预热数量、缓存 TTL 可配置，达到容量时排队或拒绝，不无限增长。

平台视图避免为每个平台复制完整节点对象。相同规则可共享不可变候选数据，但不同平台的租约与优先级仍独立。唯一 IP 视图、节点引用、正则结果都要计入内存预算，不能仅优化数据库。

冷库存不能永久饿死：为新节点、正在使用的线路、备选线路与长期未测节点分别预留调度份额。平台无合格资源时可触发受限预热，等待有期限且可观察，不在请求线程全库扫描。

## 4. 检测请求由谁发出

通过指定节点请求一个受控 HTTPS 探测地址，确实可以验证该线路连通性及被探测端看到的出口。检测任务仍由 Prism 所在机器发起和调度，消耗本机 CPU、文件描述符、连接、TLS 和带宽；出口不同不代表任务离开本机执行。

只有可以在节点机器上部署 agent 时，才可能让远端独立执行任务。普通订阅节点通常只提供代理协议，不能据此要求远端运行任意检测程序。

| 检测类型 | 推荐执行方式 | 去重对象 |
|---|---|---|
| 连通、TLS、延迟、出口发现 | 经被测线路请求受控目标 | 每条线路和必要的探测 profile |
| ASN、住宅/机房类型、信誉、名单 | 后台向允许查询指定 IP 的数据源发请求 | IP + 来源 + profile + 有效期 |
| 仅能查询当前访问 IP 的来源 | 在服务允许且确有必要时经过被测线路请求 | 按所需出口证据去重并控制费用 |
| 指定目标可达性 | 经被测线路访问允许的目标 profile | 线路/出口观测版本 + 目标 |

不能以切换出口绕过服务商账号配额或限流。来源往往按 API key、账号或产品额度限流，多个出口不会消除这些限制。不要把订阅网站 HTML 抓取当作稳定信誉接口。

通过受控 HTTPS 观察出口比信任节点名称可靠，但一次观测不能保证节点访问所有目标都使用该 IP。经常换出口的线路标为动态，不能用于要求严格固定出口的组。

## 5. 并发的容量计算

设每轮需探测 A 条线路，周期 T 秒，平均单次占用时长 L 秒，不计重试时：

```text
平均请求速率 R = A / T
平均在途并发 C = R * L
实际预算还需考虑失败超时、重试、DNS、TLS、来源限流和带宽
```

假设 A 为 1,000,000，平均 L 为 2 秒：

| 全量周期 | 平均请求速率 | 平均在途数量 |
|---|---:|---:|
| 5 分钟 | 约 3,333 次/秒 | 约 6,667 |
| 1 小时 | 约 278 次/秒 | 约 556 |
| 24 小时 | 约 11.6 次/秒 | 约 24 |

大比例失败时 L 接近超时上限，所需并发会明显上升。该表不是建议设置几千个 worker；首先根据本机能力和目标服务允许速率限制 R 与 C，反推能完成的检测周期。

推荐方案：

1. 有界到期任务队列，分健康、出口、信誉和目标探测工作池，不按库存数量启动 goroutine。
2. 同时设置全局并发、每个探测目标/数据源 RPS、每个出口并发和每节点任务互斥。
3. 抖动调度，失败退避，连续失败线路降低频率；优先检测正在使用和即将过期的资源。
4. 用户流量预留连接、CPU 和带宽余量，检测拥塞时先降低检测速率。
5. 采用可控的两个或少量探测端点，健康故障与探测站点故障分开；自建端点须规划容量，不假定公共接口支持任意高并发。
6. 必要时增加探测执行器，每个执行器有身份和独立观测范围；路径延迟与健康不能无条件跨执行器共用。

首版建议先测量 64/128/256 等并发档位下的吞吐、连接数、失败率和代理 p99，再确定默认值，不能直接把示例档位当生产最优参数。

## 6. 两种“切换”必须区分

同 IP 线路切换只改变访问路径，外部 IP 保持不变。出口切换是换到另一个合格 IP 组。两者的按钮、API、结果和日志应不同。

统一使用会话概念：`Platform + SessionKey -> 出口组 + 节点 + lease generation`。SessionKey 可以由固定用户名中的 Account、固定接入端口或反向代理参数确定；它不是认证密码。

共享同一 SessionKey 的调用者共享出口和换 IP 效果。需要独立切换的应用应使用不同会话。

## 7. 切换方案比较

| 方案 | 使用方式 | 优点 | 边界 |
|---|---|---|---|
| A 固定入口与会话，手动 rotate，推荐 | 用户名保持 `平台.会话`，调用受控操作切换绑定出口 | 适合脚本、浏览器和持续会话 | 老连接不会自动换 IP |
| B 固定端口绑定会话 | 为少量应用分配固定端口，端口关联平台和会话 | 客户端不支持复杂用户名也能使用 | 同端口使用者一起切换，不为百万节点开百万端口 |
| C 定时轮换 | 会话到指定时间后为新连接选择其他出口 | 自动化，无需每次调用 API | 必须定义没有替代 IP 时保留还是拒绝 |
| D 无粘性分配 | 新代理连接或可见 HTTP 请求重新选择 | 适合无登录状态的独立任务 | 可能选回同 IP；CONNECT 内每个 HTTPS 请求不可独立换出口 |
| E 调用上游换 IP 接口 | 给支持动态重拨的供应商发送换 IP 指令 | 同一代理地址可能获得新出口 | 依赖供应商能力，可能影响共享设备或其他会话 |

建议个人版首期提供 A 和 C，B 作为接入便利功能，D 沿用 Resin 随机模式。E 仅通过经过审核的供应商适配器提供，不允许导入任意 URL 自动执行。

### 7.1 推荐 rotate 语义

下面是建议接口，不表示 Resin 已实现：

```http
POST /api/v1/platforms/{platform_id}/leases/{account}/actions/rotate
Authorization: Bearer <scoped_admin_or_action_token>
Idempotency-Key: <operation_id>
Content-Type: application/json

{
  "require_different_ip": true,
  "expected_generation": 17,
  "existing_connections": "keep"
}
```

动作流程：读取旧出口和 generation；在同平台的合格集合中排除旧 IP 选取新候选；在需要时有界验证候选；重新检查候选版本后按会话 CAS 提交；返回新 generation、出口观测与生效范围。探测网络 I/O 不在会话锁内执行。

无候选返回 `409 NO_ALTERNATE_EGRESS` 并保留原会话，不能删除原租约后返回切换成功。并发请求的 expected generation 不符返回冲突；重复 operation ID 返回原结果，不再执行第二次切换。

Resin 当前删除租约只是释放绑定，下一次随机分配仍可能选回原 IP，因此不能直接等同于上述 rotate。上游实际出口不可证实时，响应应写明是候选选择成功还是已探测确认，不能承诺未经验证的实际 IP。

`existing_connections=keep` 为默认，新建路由使用新出口，原有 TCP 隧道继续到关闭。显式 `close` 关闭该会话已有连接，客户端须重连；这是有中断的操作，不是连接内无感换 IP。

为避免快速循环选回刚使用的出口，可增加有界的最近 IP 排除窗口。可用出口不足时明确失败或采用用户选择的降级策略，不无限重试。

### 7.2 链接入口与上游重拨

浏览器“换 IP 链接”默认打开状态与确认页面，实际变更用经认证的 POST，避免浏览器预加载、链接扫描或 CSRF 意外换 IP。脚本直接调用 POST。自动化令牌只授权指定平台/会话的 rotate，支持过期、撤销和冷却时间，不把全权限管理员 secret 放进 URL。

上游重拨属于异步任务：提交指令 -> 等待 -> 从受影响线路重新观测 -> 更新出口组与质量 -> 通过平台准入后恢复。HTTP 200 只表示指令被接收，不等于 IP 已改变。

供应商适配器必须定义控制对象和影响范围。相同出口 IP 本身不能证明同属一个可重拨设备；只有已知受该控制对象影响的线路才一起进入等待和重新检测状态。

## 8. 个人版容量档位

个人版不把“百万节点”作为默认交付承诺，按以下三档验收：

| 档位 | 库存节点 | 运行态目标 | 用途 |
|---|---:|---:|---|
| 常规 | 10 万 | 当前平台候选和近期线路进入内存 | 日常个人使用，默认性能基线 |
| 峰值 | 30 万 | 通过热/温/冷分层控制活跃 Outbound | 大订阅合并和压力回归 |
| 压力 | 100 万冷库存 | 不要求全部加载、全部检测或全部可路由 | 验证 SQLite 文件、导入和恢复边界 |

“运行态目标”不是限制用户能导入的节点数量，而是限制同时保留的完整运行对象。具体热节点上限、平台候选数量和检测并发必须通过目标硬件压测确定。常规档位通过后再优化峰值档位，不能为了压力档位过早引入分布式依赖。

在 10 万到 30 万库存范围内，SQLite 继续作为默认数据库。建议保持 `state.db`、`cache.db`、`metrics.db` 和滚动日志文件的分层；不需要因为节点数进入几十万就切换 PostgreSQL。只有出现多个写进程、远程集中管理或实测 SQLite 写入/恢复超过预算时，才增加可选存储适配器。

## 9. 本轮建议与需要测量的边界

推荐组合：SQLite 库存 + 有界热运行态 + 同出口逻辑分组 + 组内优先级故障切换 + IP 证据去重 + 分层探测 + 固定会话手动/定时换 IP。

10 万和 30 万库存要优先完成容量验证，覆盖导入、索引、启动、热节点淘汰、平台重建、检测超时、WAL 膨胀和日志留存；100 万只作为冷库存压力测试。不能沿用“已有核心测试通过”作为规模证明。未来是否分库、增加检测执行器由测试结果决定。
