# Prism v0.1.1

Bug-fix release. No HTTP route, response shape, database schema or configuration
format changed, so an existing v0.1.0 deployment upgrades in place.

## Highlights

- **Intel job scheduling no longer corrupts a settled job.** An item still
  running when the timeout sweep settled its job could write itself back to
  `done`, turning a `partial` job into `succeeded` and erasing the failure
  counts; the same window could strand an item as `queued` inside a job nothing
  would ever claim. Every item write now carries a status precondition, and the
  worker stays silent when the sweep got there first.
- **Cancelling and retrying are terminal-safe.** Cancelling a job that had
  already finished used to rewrite it as `canceled`, and retrying the failures of
  a cancelled job used to reopen it and report it as `succeeded`. Cancelling now
  applies to active jobs only (`409 CONFLICT` otherwise), and a cancelled job is
  never revived by a retry.
- **A provider's daily quota is only spent on a real request.** The budget was
  consumed before the queue was claimed, so an idle provider burned one unit of
  its daily quota per second — a 500/day source was exhausted in about eight
  minutes with no work done.
- **Exported WireGuard links parse again.** A link carrying more than one
  `allowed_ips` entry (the default is two) was rejected as `INVALID` by Prism's
  own parser, because the export side joins the list with commas and the parser
  did not split on them.
- **101 upgrade sessions keep both directions open.** The byte-counting wrapper
  around an upgraded connection did not forward `CloseWrite`, so the first
  half-close tore down both directions instead of half-closing one; its counters
  were also a data race between the two copy goroutines and the proxy's own
  reader.
- **Every listener now has connection bounds.** The served listeners were built
  as bare `http.Server` values with no `ReadHeaderTimeout`, so a client could
  hold a connection open with a half-sent header. The values existed, but on a
  server nothing ever served.

## Console

- A platform's node-selection policy can now edit **required unlock-check
  results** (`quality_policy.required_checks`). The field, its validation and the
  `GET /api/v1/intel/checks` endpoint it needs all shipped in v0.1.0; only the
  editor was missing, so the capability was unreachable from the console.
- The node list's **unlock-result filter** is now a proper rule-and-outcome
  picker fed by the API. It previously accepted a hand-typed value that only ever
  produced a `400`.
- Quality views no longer name the upstream data vendors: a result is presented as
  what it means (purity band, network traits, unlock outcome), not as which
  commercial source produced it.

## Behaviour changes to be aware of

- `intel_max_running_jobs` is now validated against an upper bound of 1024, and
  `intel_check_concurrency_per_check` against 4096. Both defaults (64 and 512)
  are far below the bounds.
- The intel runtime defaults changed: `intel_max_running_jobs` 16 → 64 and
  `intel_check_concurrency_per_check` 16 → 512, so a full pipeline is no longer
  cut off mid-step on a large job. Existing installations that already stored a
  runtime configuration keep their stored values.
- `docs/SECURITY.md` and `.env.example` now state the defaults the code actually
  applies (`PRISM_PROXY_AUTH_FAIL_LIMIT=30`, `PRISM_DENY_PRIVATE_NODES=true`,
  `PRISM_DIRECT_DENY_PRIVATE=true`). The documented values were wrong; the
  behaviour is unchanged.

## Upgrading

Nothing to do. `docker-compose.yml.example` is pinned to `0.1.1`; if you copied
it, bump the tag and pull.
