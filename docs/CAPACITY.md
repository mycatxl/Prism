# 单机容量规划与基准边界

Prism 的单机设计点是 **10,000 个注册用户、客户侧双向合计 1 Gbps**。注册人数、活跃用户、同时连接、粘性账号和节点库存是不同指标。下面给出起测规格和验收指标；最终销售上限取决于目标机器上的同步记账、加密协议、上游和出口 IP 实测。

## 设计点与起测规格

| 项目 | 起测假设或规格 |
| --- | --- |
| 账号规模 | 10,000 个注册用户，峰值 10% 活跃，即 1,000 个活跃用户 |
| 同时连接 | 每个活跃用户平均 2 条 TCP 连接，即 2,000 条；另测 10,000 条连接的压力与拒绝行为 |
| 吞吐口径 | 客户上传加下载合计 1 Gbps，即约 125 MB/s；短请求、长连接分别测量 |
| CPU / 内存 | 从 8 个专用 vCPU、32 GiB RAM 起测；保留至少 30% CPU 和内存余量 |
| 存储 | 本地、有掉电保护的 NVMe，建议可用空间至少 200 GB；容量按日志增长与备份实测调整 |
| 网络 | 建议 2.5 Gbps 或更高的全双工网卡/虚拟带宽，覆盖上下游重复经过主机和协议开销 |
| 文件描述符 | 从进程软/硬上限 65,535 起测，同时核实系统上限、临时源端口和 conntrack |
| 部署 | 一个 Prism 进程独占 state/cache/intel 目录；管理面与数据面按 [INGRESS.md](INGRESS.md) 分开暴露 |

这些规格是基准测试的起点。高 RTT、重型加密、较小传输块、大量情报任务或慢磁盘都可能使同一机器更早达到上限。当前速率、并发和带宽限制按密钥执行；用户流量额度跨密钥共享。不能把每个密钥的带宽上限直接相加当作主机容量。

1 Gbps 持续满载约产生 450 GB/小时、10.8 TB/天、324 TB/30 天的客户侧流量。Prism 主机同时接收和发出这些字节，网卡 RX+TX 合计约为客户侧口径的两倍。供应商如何计费及上游带宽配额需要分别核实。

## 同步记账是吞吐预算的一部分

发送字节前提交持久预留，写入后按实际接受字节结算；每个块通常产生两次 SQLite 同步提交。state.db 是单写入通道，记账、恢复和部分后台写入会争用它。缓存冲刷间隔和请求计数冲刷间隔不会取消这两次持久提交。

若客户侧吞吐为 `R` 字节/秒、实际平均结算块为 `B` 字节，最低记账提交需求约为 `2 × R / B`。以 1 Gbps、32 KiB 块为例，约需 **7,630 次同步提交/秒**，单通道平均提交预算约 **0.13 ms**，尚未计入短请求、握手和后台操作。若只能达到 1,000 次提交/秒，同样块大小的理想上限约为 131 Mbps。实际平均块更小时，提交需求更高。

因此必须测量 FULL 同步、WAL、真实文件系统和正常预留/结算路径；纯内存路由、no-op outbound、tmpfs 或放宽同步设置的结果不能证明 1 Gbps 持久记账容量。记录提交吞吐与 p50/p95/p99、SQLite BUSY/LOCKED、未结预留、用量刷新错误、磁盘写延迟和队列积压。存储错误时受影响访问会保持关闭，恢复流程见 [RECOVERY.md](RECOVERY.md)。

## 出口 IP 与库存预算

应统计每个平台当前满足启用、出站、健康、延迟、评分及隐私准入的**去重出口 IP**。重复协议或重复订阅中的同一出口只增加节点数，不增加 IP 供给；全池健康数量也不等于某个平台可路由数量。

设峰值活跃粘性账号数为 `A`，供应商及产品政策允许每个 IP 同时服务的账号数为 `q`，备用比例为 `s`，则起测供给为 `ceil(A / q × (1 + s))` 个合格、独立出口 IP。例如 1,000 个活跃用户各使用 1 个粘性账号，备用 25%：

| 使用策略 | 起测出口 IP 规模 |
| --- | --- |
| 每个账号需要独立 IP，`q=1` | 1,250 个 |
| 每个 IP 可承载 10 个账号，`q=10` | 125 个 |
| 同样共享策略，但每用户同时用 3 个平台账号 | 375 个 |

这是假设示例，不是默认的独占承诺。均衡路由不自动等于账号独占 IP。还要按地区、ASN、解锁能力及平台政策分别留备用，核实供应商的并发、流量和探测额度。不能从某个当前订阅包的数量推导开源项目容量。

FD 初步预算为 `2 × 活跃隧道数 + 探测连接 + HTTP 空闲连接 + 基线开销`，再留至少 30% 余量。真实 sing-box 引擎、DNS、TLS 和连接状态必须实测；no-op 测试里的近似 FD 打印值不是系统 FD 观测。

## 可复现的控制面基准

运行 `make capacity`；发布构建标签与其他 Go 检查相同。2026-11-14 本地 Go 1.27.0 / Linux 的一次结果如下，供复现比较；它们是进程内数据结构测试，不含实际网络、加密及 SQLite 逐块记账。

| 测试 | 本轮结果 |
| --- | --- |
| 平台视图重建，10k / 50k / 100k 节点 | 92.9 ms / 268.5 ms / 1.775 s |
| 节点池导入，10k / 50k / 100k 节点 | 1.141 s / 7.711 s / 21.473 s |
| 100k 节点池导入的活跃分配增量 | 约 197 MB，未包含真实 outbound 的连接成本 |
| 1,000 并发 worker、100k 路由选择 | 0.876 s，约 114k 次选择/秒 |
| 创建 50k 粘性租约 | 3.570 s |
| 20k 租约、1,000 个去重 IP 的负载统计 | 覆盖 1,000 个 IP，合计负载 20,000 |

测试源码是 `internal/platform/platform_capacity_test.go`、`internal/routing/router_capacity_test.go` 与 `internal/topology/pool_capacity_test.go`。比较结果时同时记录 CPU/配额、内存、Go 版本、构建标签、后台负载和提交号。

## 目标机器的验收指标

逐档提高 100 / 1,000 / 2,000 / 10,000 条连接；每档预热后持续运行，最后做至少 30 分钟的设计点测试。使用独立受控目标和真实加密上游，同时启用正常计量、订阅刷新、情报任务及保留清理。覆盖 HTTP 转发/CONNECT、SOCKS5 TCP CONNECT 和需要销售的反向转发路径。

记录下列指标并用实测上限设置套餐和运营容量：

- 客户侧有效吞吐、主机 RX/TX、每协议错误率和握手 p95/p99；稳定达到目标且没有持续积压。
- 管理 API p95：普通读取起测目标 100 ms，50 条节点筛选页起测目标 300 ms；同时记录大库存和多条件筛选的扫描量。
- CPU、RSS/GC、FD、临时端口、conntrack；持续利用率应保留约 30% 余量。
- 同步提交吞吐和延迟、BUSY/LOCKED、刷盘失败、未结预留、WAL/日志增长、磁盘可用空间与告警送达。
- 每个平台的可路由节点和去重 IP、探测队列、供应商配额、IP 切换及节点池全挂后的拒绝/恢复行为。
- 停止流量后，小时用量、订阅扣量和持久预留一致；重启及恢复不重复扣量，也不补发已用额度。

完成这些证据后才形成该硬件的承载声明。当前未提供共享状态集群；增加第二个进程不能扩展同一个目录的单写入记账能力。
